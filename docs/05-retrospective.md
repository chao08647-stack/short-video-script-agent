# 实现回顾与下一步

本文记录本次开发中已经观察到的问题与设计取舍，不代替候选人的个人学习陈述。测试结果持续更新在评估文档中，本文不预先宣布未执行的验证通过。

开发中已经历多个真实批次：DeepSeek [首批自动评估](../examples/deepseek-flash/summary.json) 8/14，包含内容漏检和余额中断；用户充值并修补后，[首次复测](../examples/deepseek-flash-recheck/summary.json) 达到 10/14。四份问题稿的 [AI 文件复核](../examples/deepseek-flash-recheck/content_review.json) 未再次发现原具体 UI、导出功能和单条引用问题，但不是全面质量保证或真人签字。该次四个 40 次预算失败继续推动改进，之后的 [全量批次](../examples/deepseek-flash-final) 与 [收尾定向验证](../examples/deepseek-flash-validation) 均另存。最终结果由评估文档集中汇总，不将阶段目录名称或阶段通过数当成最终结论。

## 模型能聊天不等于工具协议可用

接口预检时，模型列表与普通对话均成功，原生工具调用却返回 HTTP 400，错误指向服务端缺少自动工具选择和工具解析器配置。重测后，自动工具调用和结果回传恢复可用。

第一次成功探测中，模型同一轮提出了原稿与替代稿的两个调用。这能证明协议可以返回工具调用，但不足以证明模型观察结果后才调整下一步。因此又进行了顺序测试：先返回 30 秒超限，再由模型提出 100 字方案并重新计算为 25 秒。这一区别影响证据质量，不能把任何成功的 function call 都称为重规划。

项目因此在适配层显式请求关闭并行调用，在运行时拒绝一轮多个工具动作，并记录完整的调用—观察关系。该选择便于审核三天作品的决策链路，代价是没有利用独立工具并行执行来降低延迟。

早期 Qwen 完整脚本接入又暴露出更长参数下的协议问题：模型在普通正文输出脚本 JSON，但服务没有将其解析为 `tool_calls`。实现增加显式 `LLM_ACTION_PROTOCOL=native|json`，并在当时的本地实验中选择 JSON。仅约束“输出一个对象”的实现仍出现模型抄写定义而不提交动作的问题，随后改为严格 `json_schema`，用 `anyOf`、`const` 绑定动作和参数。错误不会自动降级格式、切换协议或变成 Mock。真实测试显示，语法约束可以限制输出结构，却不能保证模型选择了有效的下一步。

用户选择 DeepSeek Flash 后使用原生工具调用，显式关闭 thinking。当前适配器不保留推理内容用于工具回放，因此在配置阶段拒绝开启 DeepSeek thinking，也不把本地兼容服务支持的 JSON Schema 参数原样套到这个接入。模型服务、协议与推理模式必须一起验证。正常稿流程走通和超时稿确实被压缩，是有价值的执行证据；后续漏检说明这些仍不等于内容最终合格，更不能从当前单次结果推出模型能力的普遍排名。

## 上下文预算影响完整业务运行

小型工具预检成功后，完整项目曾因服务端 4K 上下文限制返回 HTTP 400。用户后来重启服务，将上下文升级为 32K，配置验证已完成；完整业务结果仍以评估记录为准。这个过程说明接口连通、工具协议可用、上下文容量足够和业务决策正确是不同层次的验证。

实现也减少重复上下文：按当前阶段提供动作 schema，发送当前稿件与检索原文、检查状态、完整错误定位和最近八次动作摘要，避免每轮回传完整历史。所有已加载技能正文每轮每份只发送一次；方向阶段也能看到用户已有初稿。完整 Trace 与 checkpoint 继续保留。较早人工意见仍不会每轮全部重发，仍需通过修订场景检查模型是否遗漏要求。提高输出 token 预算不能代替扩大服务端上下文。

DeepSeek 阶段新增每次请求 **16384 token 输入加输出预算、4096 token 输出预留**。项目使用官方 Flash-1017 的固定 tokenizer 与编码器，计入完整 prompt、工具 schema 和请求序列化开销；取两种计数较大值，加 10% 与 128 token 余量，不靠裁掉资料通过门槛。计数是本地估计，云端包装可能不同，因此响应后还核对实际 usage，超限时明确记录“请求已经发送”。这形成了一个实际取舍：更保守的预检会拒绝一些可能还能容纳的请求，但能避免把估算值冒充服务端保证。

## 人工审核与稿件版本必须一起设计

三个“确认”提示本身不能证明 human in the loop。实际需要解决的是暂停后恢复什么状态、用户批准的是哪个版本、修改之后哪些旧检查还有效，以及达到上限时是否仍能通过恢复继续无限执行。

当前实现使用稳定任务 ID、SQLite checkpoint 和独立的人审节点。方向、初稿、终稿审核各自绑定版本；修改稿件使旧检查失效。初稿批准仅确认表达，终稿批准不能豁免事实或时长问题。中断节点不承担模型调用和导出副作用，避免恢复重执行造成重复操作。

恢复操作现已增加按任务 ID 的跨进程操作系统锁，避免两个本地进程同时消费同一审核请求；退出或崩溃时锁会释放。锁与 checkpoint 解决不同问题：前者限制同时修改，后者保存状态。当前 CLI 仅支持正常停在人审门后的恢复，不把锁自动释放表述为任意节点崩溃后都能自动续跑。分布式并发审批、多用户权限和断电下的多文件导出一致性仍不在第一版保证范围内。实际验证结果见评估文档。

图自身也有执行步数保护。固定图步数可能在用户配置较大调用预算时先中断，来不及保存明确的“预算耗尽”结果；当前运行时按配置预算计算递归上限，让业务计数器负责有界停止。高预算回归与导出结果在评估材料中记录，不把增大图步数解释为取消调用限制。

## 16 个技能需要可观察差异

“增加到 16 个 SKILL.md”很容易，证明每个技能在合适场景中实际影响结果更困难。拆分时使用产出边界：叙事结构输出大纲，分镜编排输出镜头组织，画面描述输出可执行动作；来源绑定建立映射，事实修订处理检查发现的问题。

运行记录分别保存加载事件、模型声明的使用关系以及候选关联。仅统计文件数或加载次数会夸大能力；评估仍需检查技能之后实际出现了什么查询、修改或产物。完整覆盖以真实记录为准，没有覆盖的技能应明确列出，而不是安排程序偷偷替模型逐项加载。

实际失败循环中，模型曾加载全部 16 个技能而没有交付合格稿件。这使“加载覆盖率”与“有效使用率”的差异变得具体：需要观察技能之后是否发生了正确查询、实质改稿和通过检查，而不能把遍历技能当成能力增长。当前实现因此禁止重复加载，并持续保留已加载正文，但这项工程约束仍不能替代效果验证。

收尾中为 `missing_info`、`query_rewrite`、`skill_showcase` 明确指定相关技能，是为了观察方法是否被实际应用。必须因此收窄结论：这是定向应用证据，不是自主路由能力，也没有证明技能相对不使用时带来增益。showcase 原要求就是三个镜头，出现四镜头时照常记为未通过；后续只把分工明确为 S1/S2/S3，并排除额外 P03 样式内容，没有把数量要求改成四个来迎合输出。

## 估时与事实核验都有边界

早期真实接入进一步暴露了两个问题：结构化格式正确不代表模型会行动，模型可能把加载压缩方法误当成已经改稿；要求每次重新生成完整稿，容易出现原样复制及引用文字失配。项目因此增加局部 `patch_script`。底层一直支持最多 20 项原子编辑，早期给模型的 schema 却只允许每次一项。首次修补复测暴露出这个限制的代价：改旁白后旧 claim 暂时失配，再改字幕与引用又需要多轮，零碎修订消耗了调用预算。

现在同一次工具动作允许最多 20 项关联编辑，旁白、字幕、画面与对应引用可以一起更新；先替换，再按降序删除数组项，整组失败则不保存。需要新增 claim 或更大改写时仍可完整提交。这里保留“一轮一个工具动作、观察后继续”，改变的是该动作的原子修改范围。后续完整批次已有原子多处修改并完成审核的证据；再重复的人审任务仍耗尽60次，因此不能据单次成功宣称稳定收敛。

估时是可解释的文本模型，不是真实配音测量。字幕和旁白并行时不能重复相加，数字、缩写和演员节奏也不能被字符计数完美刻画。项目选择固定规则并公开假设，便于复现和指出误差。

引用 ID 和原文存在只能证明引用有效，不能证明原文支持所有改写。项目将确定性检查与独立模型核验分开，保守处理不支持和不确定结果；当前两部分模型工作都由 DeepSeek Flash 承担，同一个模型的另一轮提示词仍可能出现相似偏差，不能宣称有外部事实保证或已经杜绝幻觉。

首批记录已观察到具体漏检：`normal`、`missing_info`、`tool_failure`、`duration_revision` 把来源中没有的按钮、滑块、进度条、时间线或面板写成真实录屏；缺信息场景还带入未获支持的导出操作。正常稿的一条复合 claim 把自动生成与手动修改合在一起，却只引用支持其中一项的原文。即使同镜头另有别的来源，这一条引用仍不能独立支持完整断言。原自动核验没有拦住这些问题。

修补分为三部分：规则文件增加功能／UI 的 `evidence_required_terms`，扫描已知字面词及同字段证据；核验提示要求检查全稿中未声明的产品操作，并逐条检查 claim 自身引用；结果增加 `semantic_status`，语义调用失败另存 `semantic_error`。四个问题场景已在首次修补复测中另存新结果，有限审阅没有再次发现上述具体旧问题；旧 Trace 没有改写。词表仍可能误报含“按钮”等词的否定描述，模型对口语改写的支持判断仍有波动，因此不能宣布全面语义保障。

之后又发现引用需要逐镜头落实：前一镜头已有资料，不能自动支持后一镜头的产品功能介绍。新增 `scene_evidence_terms` 后，出现配置功能短语的镜头必须有自己的来源 ID 和有效的显式 scene claim。它只检查这类镜头是否完全缺少本镜头证据，不会因找到一条 claim 就保证所有文句正确。对实际稿件的评价还须区分确定的无依据产品事实、需要确认的隐含含义和主观创作措辞；文风不合偏好本身不是事实造假。

另一个误报出现在型号：原文已有 `H1`，数字规则却把其中的 `1` 当成性能数字要求补证。现在仅豁免原文确实存在的完整字母数字型号内部数字，不豁免型号之外的百分比、续航等数据。这说明确定性检查也需要反例，收紧事实边界时不能忽略误报成本。

## 反馈必须跨字段落实，停止也是合法决策

首次复测的人工反馈场景出现只修改旁白、字幕仍保留开场反问的情况。`human-feedback` 升级为 1.1，要求逐项核对标题、旁白、字幕、画面与引用；固定用例同时检查首镜旁白和字幕不再有问号。`visual-direction` 也升级为 1.1，给出不代表真实 App 交互的抽象字幕动画示例。技能变更保留版本差异，不能把新指引套用到旧 Trace 上声称已经生效。

过短时长场景还暴露出提示偏置：“普通修正不要问用户”有助于减少无谓请示，却也可能让模型一直改稿而不提出真正需要确认的硬性约束。当前提示把真实压缩、请求调整时长、说明不可行并列为模型可选动作，依据实际估时决定；没有针对 1 秒写死分支，也不允许自行改变目标。

后续 `too_short` 出现了安全但提前的追问，没有形成该用例要求的工具测量证据，因此仍判未通过。收尾输入明确先提交保留两项功能的最短候选稿、实际估时，再选择下一步。这里改进的是测试指令的可检验性，不能把安全追问说成越权，也不能用主观“显然超时”替代要求提交的测量记录。

`human_feedback`、`headphones`、`query_rewrite` 三份复杂输入显式提高到 60 次模型请求、80 次工具调用，其余普通输入保持 40/60。这个取舍允许更长的检索和修订链，也提高潜在成本；后续完整批次三例实际分别用23、34、17次完成，最后人审重复试验又耗尽60次。各次代码和输入不同，不能解释为同条件能力提升。

## 服务中断留下的是验证缺口

首批另外六个场景返回 HTTP 402／余额不足。这是服务不可用证据，不是模型在业务决策上必然失败的证据。用户随后充值，真实复验持续推进，首次修补复测及后续全量／定向批次分别保存。旧错误与部分产物仍保留；之后的预算耗尽、未测量就追问或镜头数量不符是各自新的实际问题，不能继续归为余额阻断，也不能用 Mock 补写为真实通过。

## 依赖安装也需要留下真实记录

初次创建虚拟环境后，安装过程曾遇到构建隔离阶段停滞和下载 wheel 超时。开发流程改为显式访问包索引、延长读取超时并保留工作区缓存。当前环境已能读取到 LangGraph 1.2.18 和 `langgraph-checkpoint-sqlite` 3.1.2，完整版本保存在 `requirements-lock.txt`；这只能说明本地安装状态，换环境能否复现仍要实际执行安装和测试，不能把锁文件的存在当作验证成功。

## 后续改进顺序

1. 现有收尾结果、逐镜头引用、三镜头约束及先测量后决策的证据已汇总到评估文档。后续新增验证应先制定总预算，再延续同样的记录方法。保留各批次输入、预算、代码／技能版本及复核差异，不能把定向指导后的成功混算成自主路由或不变条件下的增益。
2. 为事实支持度增加人工标注的断言—原文样本，分别统计漏报和误报，并比较不同核验模型。
3. 在仍保留文本估算入口的前提下，可选接入真实配音测时，评估估计时长与实测偏差；这属于后续扩展，不是本题必做视频合成。
4. 增加资料补充的版本化导入，使用户能在同一任务中补证，并明确哪些检查和审核需要失效。
5. 有多人使用需求时，再补用户权限、分布式审批互斥、运行队列、导出原子性与可视化审核界面。

本次续作的开发／验证记录覆盖 2026-10-30 23:53 至 2026-10-31 01:25（Asia/Shanghai），约 1 小时 32 分钟；后续归档及提交材料核对另计。实际结果和未完成项见评估文档，时间依据见 [进度记录](../progress.md)。以上是 AI 辅助开发中实际观察到的反馈，不伪写成候选人的个人学习经历；候选人后续修改和体会应另附可核对记录。

最终收尾：四批实际usage合计5,838,719 tokens（包含缓存计数，不是费用金额），第二次HTTP 402后停止模型调用。321项工程测试通过，最新失败和总调用消耗已进入评估文档。后续应先建立整个实验的费用／调用预算，减少全量反复跑测，针对核验一致性与返修收敛做小范围对照。
