# AI 辅助使用记录

## 记录原则

本项目允许并实际使用 AI 辅助。以下区分用户作出的产品决定、AI 协助生成的实现，以及需要通过执行证明的结果。文档不把 AI 生成代码冒充候选人手写代码，不把计划、示例或 Mock 输出冒充真实模型运行结果。

## 用户已作出的贡献

用户提供了四道考核题及交付规则，经过比较后排除了知识问答方向，并选择进一步实现第 4 题。用户确认了以下设计决定：

- 主语言 Python，使用 LangGraph。
- 需要 15 个以上业务技能包，最终按 16 个独立技能设计。
- 技能按需加载，由整套验证用例覆盖，而不是每次任务全部执行。
- CLI 入口，创作方向、初稿和终稿均人工审核。
- 用户仅提交修改意见，由模型修改脚本，不直接替换稿件。
- 按题面使用产品素材与品牌规则，通过兼容 API 调用真实模型。

用户提供了本地模型接口地址和模型名称，并在首次工具协议测试失败后要求重测。对话证据只能说明第二次测试时接口支持了原生工具调用；没有证据说明服务端具体由谁、采用什么命令修改，因此不虚构这部分个人贡献。

完整项目随后遇到服务端 4K 上下文限制。用户明确重启服务并将上下文升级为 32K，后续预检确认配置可用。这属于实际发生的环境支持贡献；它不代表完整业务验收或全部技能验证已经通过。

后续用户选择 **DeepSeek Flash 作为主模型**，采用原生工具协议，明确关闭 thinking，并要求控制单次输入加输出预算。这是本阶段实际的模型与资源约束选择。没有把更换模型写成候选人手写接入代码，也没有把评估器的自动回复归为用户本人逐稿审核。

首批请求遇到 HTTP 402／余额不足后，用户已经充值，真实模型复验随后继续。充值及继续验证属于用户提供的实际运行条件，不把这些记录写成用户编写了后续修补代码或已经真人批准全部稿件。

## AI 协助范围

开发过程使用 Codex 及并行 AI 协作代理。其工作包括选题与开源参考调研、方案细化、项目代码、工具和类型定义、16 个技能指引、合成数据、测试、运行记录整理以及说明文档。并行代理分别承担工具／schema、技能／数据、模型适配等模块，主代理进行集成与验证。

这些文件目前均属于 AI 辅助开发成果。仓库没有在本文编写时记录到候选人独立手写的功能或修改，不以“本人重构”“本人修复”等表述填补空白。候选人后续阅读、修改或验证时，应按实际文件、commit 和结果追加记录。

真实测试暴露的协议格式、重复动作和引用修订问题，也是由 AI 开发代理据 Trace 调整代码：包括严格 JSON Schema、当前状态的动作前置条件、局部 `patch_script` 与相应回归测试。这些是开发助手完成的工程修改，不归为候选人独立编写，也不能把新增机制当成运行时模型已经学会正确修订。

DeepSeek 适配、关闭 thinking 的配置校验、官方 tokenizer 资产的来源与指纹记录、完整请求预算估计、响应 usage 检查，以及对应测试和文档也由本次 AI 开发代理协助完成。开发代理可以依据失败记录修改实现并重新运行评估；这些开发期干预应与运行时模型自主选择动作区分。Trace 来自实际调用，不由开发代理预写工具结果或替换为 Mock。

自动评估后，Codex 又逐项审阅保存的稿件与来源，发现自动规则和运行时模型核验漏掉的界面细节、导出功能及复合引用问题。[manual_audit.json](../examples/deepseek-flash/manual_audit.json) 明确标记审阅者为 `ai_assisted_repository_review`、`human_signoff=false`。文件名中的 manual 表示自动验收之外的文件复核，不代表候选人或用户真人逐项签字。配置化 `evidence_required_terms`、全稿及单条引用核验提示、`semantic_status` 和 `semantic_error` 记录也由开发代理补充；修后真实结果已经另存，未覆盖首批记录。

后续原子 patch 范围调整、两项技能升级至 1.1、H1 型号数字例外、`scene_evidence_terms` 逐镜头证据规则，以及收尾输入和验收修正，同样属于 AI 协助的开发期干预。部分输入明确指定技能，用于定向应用验证；它们不构成自主技能选择或技能增益的证明。调整 `too_short` 的测量步骤、把 showcase 的原三镜头约束明确为 S1/S2/S3，均保留实际输入和版本差异，不把后来改进的指令冒充早期运行时已有条件。

选题阶段检查过 MoneyPrinterTurbo、NarratoAI 等开源仓库，主要用于理解相关产品的范围及其与考题的差距。当前实现采用独立的小型脚本 Agent 结构；框架承担的职责在方案文档中列出，不把 LangGraph 本身的能力写成项目作者重新实现的能力。

## 项目运行时的模型与 Mock

项目运行时模型与开发助手是两个不同角色。早期运行时模型为 `qwen25-14b-pbn-answer`，当前主模型为 `deepseek-flash`，通过可配置的 Chat Completions 接口调用。运行时模型负责实际选择动作、生成或修订脚本，并通过单独核验提示词检查事实支持度。DeepSeek 的这次事实核验仍是同一个模型的另一请求，不是独立外部认证。

离线 Mock 是明确的测试替身，用于验证图的状态转移、错误处理、审核恢复与导出。Mock 的固定行为不能证明真实模型会选择正确工具，也不计入真实技能或动态决策效果。

评估程序中的预设批准或修改意见是“模拟人类回复”，应在记录中标为 `evaluation_simulated_human`。它能检验 HITL 程序链路，但不能冒充真实用户对创作质量的认可。

## 已发生的验证与证据边界

接口预检实际观察到了：首次普通对话成功、工具请求因服务端工具解析配置缺失而失败；重测后，模型先调用工具计算 120 字在每秒 4 字条件下为 30 秒，观察超过 25 秒限制后，下一轮选择 100 字重新调用，获得 25 秒并结束。这只证明小型原生工具反馈循环可用，不是完整脚本项目的验收结果。

完整项目的测试命令、真实输出、失败和限制以 [评估文档](03-evaluation.md) 及其引用的运行文件为准。技能包和覆盖用例由 AI 编写不代表真实模型已全部采用；应分别核对 live 与 Mock 的加载事件、声明、候选关联和实际产物。文档中的合成初稿明确标记为“用户提供初稿”这一输入角色；例如超时初稿由 AI 构造为测试夹具，不声称它由本次运行模型先生成，也不声称候选人实际手写了这份初稿。

早期 Qwen 批次保留 [3/14 的历史结果](../examples/live/summary.json)，开发期多阶段失败保存在 [examples/experiments](../examples/experiments)，没有改写为成功 Trace。一次失败循环中的 16 技能加载也不是能力验证。DeepSeek [首批自动结果](../examples/deepseek-flash/summary.json) 为 8/14，文件复核发现四例内容问题；充值后的 [首次修补复测](../examples/deepseek-flash-recheck/summary.json) 为 10/14，对四份问题稿的 [有限内容复核](../examples/deepseek-flash-recheck/content_review.json) 未再次发现原具体问题。这些历史批次不是统一冻结条件下的模型能力排名，也不是当前最终结果。

首批六例 HTTP 402 记录保留为当时的服务余额失败，不能归因于模型业务能力，也不能继续表述为当前余额阻断。后续批次在 [deepseek-flash-final](../examples/deepseek-flash-final)，收尾定向验证在 [deepseek-flash-validation](../examples/deepseek-flash-validation)。最终自动统计、内容审阅、工程测试和未通过项集中引用评估文档，不在本文件预报尚未确认的数字。原始 `acceptance_passed`、稿件及 Trace 保持不变，补充审阅结论与新的代码修改分开记录。

所有自动运行中的人审回复均为 `evaluation_simulated_human`；文件复核也属于有限的 AI 辅助审阅。审阅意见区分明确缺失来源的产品事实、含义不确定的表达和主观创作建议，不能把文风偏好记成已确认事实造假，也不把“未发现问题”写成真人签字或全面质量保证。

本阶段记录的开始时间为 **2026-10-30 23:53（Asia/Shanghai）**，工作跨至 2026-10-31 继续；最终结束时间与耗时由主开发在完成后补记。这不是整个项目首次启动时间。实际投入用时不套用题面的建议时长，也不把并行代理工作时间直接累加成候选人工时。

## 候选人后续可补充的真实记录

后续提交者应核对功能边界、复现命令和引用证据，并只追加真实发生的内容：修改了什么、为什么修改、采用哪个 commit、运行了哪些检查、实际结果如何。尚未发生的个人复核不能提前写成“已完成”。密钥、隐私数据和模型内部思维过程不应出现在公开记录中。
